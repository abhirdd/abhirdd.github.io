blob: URL origin-segment forgery probe — can "null" become "google.com"?

Anatomy first: a blob URL is blob:<SERIALIZED ORIGIN OF THE CREATING REALM>/<UUID>. The origin segment is generated browser-side inside URL.createObjectURL() from the origin of the realm that called it — it is not a page-controlled string, there is no parameter for it. The BlobURLStore also resolves lookups keyed by (origin, UUID), so a hand-forged blob:https://www.google.com/… that was never registered by a google.com realm simply fails to resolve. Conclusion being proven below: blob:google.com/… can only be minted by code running at google.com — impossible without an XSS there. Also remember the two UI fields are independent: the "From" line reads the initiator origin; the copy-link URL reads GetURL() = the blob URL itself. Forging one never moves the other. Inert .txt probes; your V4 observation (From hidden + blob:null/<uuid> copy-URL) is the reportable artifact — packaging at the bottom.

Dispatches anchors with hand-forged hrefs blob:https://www.google.com/<uuid>, blob:google.com/<uuid>, blob:https://google.com/<uuid>. Expectation: zero rows appear (store lookup fails). A row appearing with a google segment = BlobURLStore validation bug → crbug immediately.

B4 — REAL foreign blob:null, dispatched by top
