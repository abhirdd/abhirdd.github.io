Initiator-binding deep fuzz — hunting "From google.com" WITHOUT redirects

Honest threat model first: post-patch (Chromium CL ae2cc7a, feature kDownloadsDisplayInitiatorOrigin, default ON) the "From" line renders FormatOriginForSecurityDisplay(GetRequestInitiator()), and that initiator origin is bound browser-side to the committed origin of the frame that dispatched the download. No page-side function can write "google.com" into that field on a default patched Chrome. The only non-redirect routes that can ever produce a google.com attribution are: (R3) a NEW mis-attribution bug in the initiator binding — which is exactly what this page attacks with context-manipulation primitives, including two deep ones (X7 opener-chain laundering, X8 named-window resurrection) that put a real google.com-committed window into your download's auxiliary/creator chain via direct navigation, zero redirects; or (R2) serving from an origin you own whose formatting reads like google.com (homograph) — requires domain registration and surviving Chrome's IDN anti-spoofing, which this page deliberately does not operationalize. Expected on current Chrome: every row holds = patch-robustness evidence. A google string in ANY row = initiator mis-attribution jackpot → crbug FIRST, publish later. Inert .txt probes only.

X0 — DEAD-LEVER LEDGER (no button)

Already-dead page levers, kept here so you don't waste runs: referrerpolicy/rel (not fed to initiator) · Referrer header via fetch (forbidden header) · pushState/replaceState to google.com (cross-origin, blocked) · <base href="https://google.com/…"> (resolves URLs, never changes origin) · document.domain (X2 probes it; github.io is a public suffix) · blob minting (origin baked at creation, X5 probes it).

X1 — CONTROL: gesture download, top document

Baseline. Expectation: "From" = your true origin string. Every other row diffs against this.

X2 — document.domain ORIGIN-SETTER ATTEMPT

The only page-side API that ever mutated an origin. Attempts document.domain = parentSuffix then gesture-downloads. Expectation: setter blocked (deprecated + public suffix) and From unchanged even if the setter lands.

X3 — SANDBOX allow-same-origin (control for X4)

sandbox="allow-scripts allow-same-origin allow-downloads" srcdoc iframe, sync fire while reachable. Expectation: From = your origin (origin preserved through sandbox).

X4 — OPAQUE SANDBOX (origin=null) via postMessage

Sandboxed iframe without allow-same-origin: opaque initiator, auto download. Expectation: From empty. From = top origin = launder bug. From = anything else = mis-attribution.

X5 — FOREIGN blob:null MINT (creator≠dispatcher)

Opaque iframe mints a blob:null/… URL; the TOP document clicks an anchor whose href is that foreign blob (creator realm = opaque, dispatcher = top). Probes whether initiator resolves from blob creator vs dispatching document — and whether the foreign blob resolves at all.

X6 — ADOPTED ANCHOR, SYNCHRONOUS GESTURE

Node+blob created in popup realm, adoptNode() into top, clicked inside the gesture task. From present = patch holds; From empty = gesture/initiator binding lost across realm adoption (the differentiator from the S5 auto variant).

X7 — OPENER-CHAIN LAUNDERING (google commits into your chain)

Builds W1(self)→W2→W3 all attacker-scriptable; then W2 direct-navigates to https://www.google.com/ (navigation, not a redirect). Downloads fire from W3 pre-commit (x7a), from a W2-minted blob (x7b), and post-commit (x7c/x7d). If any initiator resolution walks the opener/creator chain, it now literally sees google.com. From = google anywhere = jackpot.

X8 — NAMED-WINDOW RESURRECTION

Opens google.com directly in a NAMED window; after commit, re-targets that same named window to about:blank (opener may navigate its own auxiliary) and fires a download from the resurrected document. Any code path reading "previous committed origin" would see google. Log + read From.
